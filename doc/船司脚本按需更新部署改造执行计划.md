## 1. 改造目标

在多台生产机器环境下，实现按船司的脚本版本化发布与批量更新：

1. 一次修改只影响目标船司的队列 Worker。
2. 支持灰度发布、全量发布、失败暂停和版本回滚。
3. 所有发布版本具备 manifest、sha256、审计记录和状态跟踪。
4. 生产机 Agent 通过中心命令下载、校验、替换、重启目标船司 Worker。
5. 新增部署控制数据全部落在新库 `queue_control_deploy`，不改写原队列控制业务数据库。

本次改造不包含：

1. 新机器初始化自动化。
2. 新船司首次接入自动化。
3. Docker / Kubernetes 化改造。
4. 依赖变更的全自动升级；依赖变更仍按 `platform` 级发布谨慎处理。
5. 将原队列控制数据库迁移到新库；原库继续服务现有队列控制业务。

## 2. 数据库改造硬性边界

### 2.1 原数据库约束

当前队列控制平台默认数据库来自：

```text
QUEUE_CONTROL_MYSQL_URL
默认：mysql://queue_control:queue_control@127.0.0.1:3306/queue_control
```

原数据库固定作为“只读数据源”接入本次部署改造。

禁止对原数据库执行以下操作：

1. `CREATE TABLE`
2. `ALTER TABLE`
3. `DROP TABLE`
4. `CREATE INDEX`
5. `CREATE TRIGGER`
6. `CREATE EVENT`
7. 新增存储过程
8. 新增外键
9. 修改字段、字符集、索引、分区
10. 由部署控制服务执行 `INSERT` / `UPDATE` / `DELETE`
11. 在原库创建部署相关表

允许操作仅限：

1. `SELECT`
2. `SHOW`
3. 读取 binlog
4. 读取表结构信息

推荐为部署同步创建独立只读账号，权限至少满足：

```sql
-- 账号名、密码和 host 按实际环境调整。
CREATE USER 'queue_deploy_reader'@'%' IDENTIFIED BY '<strong-password>';
GRANT SELECT ON queue_control.* TO 'queue_deploy_reader'@'%';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'queue_deploy_reader'@'%';
FLUSH PRIVILEGES;
```

> 如果生产 MySQL 未开启 binlog 或无法授予复制权限，必须先停下来确认运维方案。  
> 不允许为了实现同步而在原库增加触发器或变更原表结构。

### 2.2 新数据库

新增本地数据库，库名固定：

```text
queue_control_deploy
```

新库职责：

1. 保存原库同步镜像数据。
2. 保存发布版本、制品元数据、发布目标、发布状态。
3. 保存部署命令审计。
4. 保存同步位点和对账结果。
5. 为中心发布服务和 Agent 下载接口提供数据支撑。

推荐账号：

```sql
CREATE DATABASE IF NOT EXISTS queue_control_deploy
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

CREATE USER 'queue_deploy_app'@'%' IDENTIFIED BY '<strong-password>';
GRANT ALL PRIVILEGES ON queue_control_deploy.* TO 'queue_deploy_app'@'%';
FLUSH PRIVILEGES;
```

新增环境变量：

```env
# 原队列控制库，只读。
QUEUE_CONTROL_SOURCE_MYSQL_URL=mysql://queue_deploy_reader:<password>@127.0.0.1:3306/queue_control

# 新部署控制库，可读写。
QUEUE_CONTROL_DEPLOY_MYSQL_URL=mysql://queue_deploy_app:<password>@127.0.0.1:3306/queue_control_deploy

# 部署控制 Redis 可复用现有 Redis 实例，但必须使用独立 stream 前缀。
QUEUE_CONTROL_DEPLOY_REDIS_URL=redis://127.0.0.1:6379/1

# 制品存储根目录，中心平台持久卷。
DEPLOY_ARTIFACT_ROOT=/var/lib/wise-rpa-queue-control/releases
```

### 2.3 数据同步范围

原库当前核心表：

| 原表 | 是否同步 | 新表名 | 说明 |
| --- | --- | --- | --- |
| `devices` | 同步 | `mirror_devices` | 设备主数据和 token hash，用于下载鉴权 |
| `queue_assignments` | 同步 | `mirror_queue_assignments` | 队列与设备绑定关系，用于计算更新目标 |
| `queue_statuses` | 同步 | `mirror_queue_statuses` | 队列当前运行状态快照 |
| `queue_commands` | 同步 | `mirror_queue_commands` | 原队列控制命令审计，属于业务审计数据，不是普通日志 |
| `queue_events` | 不同步 | 不创建 | Agent 事件流落库数据，属于运行日志 / 事件日志，数据量大且不是发布目标计算必需数据 |

同步排除规则：

1. 不同步 `queue_events`。
2. 不同步文件日志、文本日志、截图、录屏、浏览器 profile。
3. 如果原库后续新增 `*_log`、`*_logs` 类表，默认排除。
4. 如果后续出现既像业务数据又像日志的表，必须先在本文档登记是否同步，再开发。

### 2.4 同步方式

推荐使用 MySQL binlog CDC 做增量实时同步：

1. 原库不需要新增触发器。
2. 不需要修改原表。
3. 可以捕获 `INSERT` / `UPDATE` / `DELETE`。
4. 可通过 GTID 或 binlog file / position 保存位点。
5. 对原库压力低于高频轮询。

同步器要求：

1. 初始执行全量快照。
2. 全量完成后从快照位点开始增量消费。
3. `INSERT` / `UPDATE` 按主键幂等 upsert。
4. `DELETE` 同步删除目标镜像表记录。
5. 位点保存在新库，不保存在原库。
6. 定期做行数、关键字段、checksum 抽样对账。
7. 同步异常不能写坏新库，必须停在安全位点并告警。

## 5. 发布单元判定规则

### 5.1 路径规则

| 变更路径 | 发布单元 | 是否允许按单船司更新 |
| --- | --- | --- |
| `app/spider/ZIM/**` | `carrier:ZIM` | 允许 |
| `app/spider/MSCGW/**` | `carrier:MSCGW` | 允许 |
| `app/spider/common/**` | `spider-common` / `platform` | 禁止伪装成单船司 |
| `app/core/**` | `platform` | 禁止 |
| `app/queue/**` | `platform` | 禁止 |
| `app/control/**` | `platform` | 禁止 |
| `pyproject.toml` | `platform` | 禁止 |
| `uv.lock` | `platform` | 禁止 |
| `funboost_config.py` | `platform` | 禁止 |

### 5.2 打包规则

1. 只能从 Git commit 打包，不能从本地未提交文件直接打包。
2. 单船司包只允许包含 `app/spider/<CARRIER>/`。
3. manifest 必须声明受影响队列。
4. manifest 必须声明 sha256。
5. `dependencyChanged=true` 时强制 `platform` 级发布。
6. 如果 diff 同时包含公共代码和船司代码，release 工具必须失败，要求拆分或走 `platform` 发布。

## 6. Agent 升级流程

### 6.1 单船司更新步骤

1. Agent 收到 `upgrade` 命令。
2. 判断本机版本是否已经等于目标版本，已相同则直接返回成功。
3. 下载制品到临时目录。
4. 校验 sha256。
5. 校验 manifest 的 `releaseUnit`、`paths`、`queues`。
6. 禁止 zip 路径穿越。
7. 禁止包内出现非 manifest 声明的业务源码路径。
8. 解压到 staging 目录。
9. 执行 Python 编译检查。
10. 执行路由 import smoke test。
11. 找到本机上属于该船司的队列。
12. 对目标队列执行协作式排空。
13. 等待目标 Worker 停止拉取消息并退出。
14. 备份当前 `app/spider/<CARRIER>`。
15. 原子改名或移动新目录到生效路径。
16. 按原期望状态恢复队列。
17. 上报命令结果。
18. 上报心跳版本。

### 6.2 失败处理

任一步失败：

1. 不确认部署命令成功。
2. 上报 `deploy_command_result(ok=false, error=...)`。
3. 保留旧版本备份。
4. 如果目录已部分切换，立即回滚旧目录。
5. 目标设备在 rollout 中标记 `FAILED`。
6. 平台暂停后续批次。

### 6.3 目录替换顺序

```text
runtime/deploy/staging/<release_id>/
runtime/deploy/backup/<carrier>/<old_version>/
app/spider/<carrier>/
```

推荐流程：

```text
1. 新目录准备完成并通过校验。
2. app/spider/<CARRIER> 改名为 backup 路径。
3. staging 中的新目录改名为 app/spider/<CARRIER>。
4. 如果第 3 步失败，把 backup 改回原路径。
5. 只有恢复成功后才恢复队列。
```

所有新增方法、函数、类必须写清晰中文注释，至少包含：

1. 方法用途。
2. 入参说明。
3. 出参说明。
4. 核心逻辑。
5. 必要时说明异常、事务边界、幂等性。

推荐格式：

```python
def calculate_release_targets(release_unit: str) -> list[dict[str, str]]:
    """计算指定发布单元需要更新的目标设备列表。

    Args:
        release_unit: 发布单元名称，例如 ``carrier:ZIM``。

    Returns:
        返回目标设备列表，每个元素包含：
        - ``deviceId``：设备 ID。
        - ``affectedQueues``：该设备上属于当前发布单元的队列名列表。

    核心逻辑:
        1. 从 ``queue_catalog`` 查询发布单元下的所有队列。
        2. 从 ``mirror_queue_assignments`` 查询这些队列当前绑定的设备。
        3. 按设备聚合受影响队列并去重。
    """
```

### 7.2 原数据库访问规范

所有访问原库的新代码必须满足：

1. 使用只读连接配置。
2. 不执行 DDL。
3. 不执行 DML。
4. 不创建触发器。
5. 不调用存储过程。
6. SQL 中不得出现 `INSERT INTO queue_control.*`、`UPDATE queue_control.*`、`DELETE FROM queue_control.*`。
7. 单元测试必须检查禁用 SQL 关键字。
