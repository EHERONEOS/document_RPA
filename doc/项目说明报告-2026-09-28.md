## 1. 项目定位

Wise RPA 是一个面向船司单证业务的分布式浏览器自动化系统。它从 RabbitMQ 接收任务消息，按队列名路由到不同客户、船司和业务流程，使用 DrissionPage 驱动 Chromium 完成登录、页面填单、文件上传、截图、录屏和结果回传。

当前代码树由四类主要运行部分组成：

1. **设备侧 RPA Agent / Worker**
   - 入口：`app.main`
   - 接收中心平台下发的队列分配，为每个队列维护独立 Worker 进程。
   - 消费 RabbitMQ 消息并执行具体 RPA 业务。

2. **中心队列控制平台**
   - 入口：`queue_control_platform.server.main`
   - 提供设备注册、队列分配、暂停/恢复/重启、状态落库和 Web API。
   - 使用 Redis Streams 作为控制命令和状态事件通道，使用 MySQL 持久化。

3. **RPA 执行日志服务**
   - 已合并进中心队列控制平台，不再要求独立部署。
   - 接收 Agent 的执行记录、过程日志、失败原因和记录文件。
   - 提供执行日志查询接口与局域网文件访问。

4. **日志/控制台前端**
   - 目录：`rpa-log-web`
   - React + Ant Design + Vite 单页应用。
   - 提供设备管理、队列管理、日志列表和执行详情抽屉。

## 3. 总体运行架构

```text
中心控制台 rpa-log-web
        │ HTTP /api
        ▼
queue_control_platform FastAPI 服务 :8766
        │                │
        │                └── MySQL：设备 / 队列分配 / 命令 / 日志
        ▼
Redis Streams
   ├── queue-control:commands:<DEVICE_ID>
   └── queue-control:events

设备侧 app.main / QueueControlClient
        │ 读取命令、上报状态
        ▼
QueueSupervisor
        │ 一个队列一个 Worker 进程
        ▼
PausableRabbitmqConsumer / Funboost
        │ RabbitMQ task JSON
        ▼
build_task_context → 全局路由 → 船司 router → BaseRpaTask
        │
        ├── 浏览器启动 / 账号槽位协调
        ├── 页面 DOM / HTTP / 截图 / 录屏
        ├── OSS 或局域网文件存储
        ├── 业务结果回传
        └── RPA 执行日志旁路上报
```

核心设计点是“控制面”和“业务执行面”分离：

- 控制命令不直接修改业务消息，而是由设备 Agent 接收后管理本地 Worker 生命周期。
- 每个队列使用独立操作系统进程，暂停会停止拉取新消息并等待已接收任务结束。
- 恢复或重启会启动新 Worker 进程，从而加载磁盘上的最新代码。
- 日志上报是旁路逻辑，创建、写日志或终态上报失败时不应阻塞业务执行。

### 6.2 配置层

`app/config` 负责把 `.env`、Nacos 和组件参数整理成运行配置：

- `APP_ENV`：`local / test / prod`。
- `NACOS_ENABLED`：决定是否从 Nacos 加载共享配置。
- `QUEUE_ASSIGNMENT_SOURCE`：
  - `server`：由中心平台下发队列；
  - `local`：只按 `RPA_QUEUES` 启动本地监听。
- `RPA_QUEUES`：本地队列或平台失联时的兜底队列。
- RabbitMQ 连接默认来自 Nacos 的 `rabbitmq.yml`。
- 浏览器端口池默认 `10000-48000`。
- 单队列默认并发 3、QPS 3。
- 同一账号默认最多 3 个浏览器槽位，空闲回收时间默认 60 秒。
- `ENABLE_BROWSER` 用于控制本地调试是否启动真实浏览器。

`.env.example` 中包含设备 ID、注册令牌、控制 Redis、中心 MySQL、执行日志服务 URL 和 Token 等模板配置。真实 `.env` 不应提交到仓库。

### 6.3 队列控制 Agent

入口链路：

```text
app.main
  → app.control.queue_client.main.main
  → QueueClientSettings.from_environment
  → QueueControlClient.run_forever
```

`QueueControlClient` 的主要职责：

1. 启动设备级 `AccountSessionCoordinator`。
2. `local` 模式下按 `RPA_QUEUES` 直接注册队列。
3. `server` 模式下连接控制 Redis，读取命令并上报状态。
4. 周期发送设备心跳。
5. 平台不可达或长时间未下发时，可按本地兜底队列继续工作。
6. 收到 `assign / unassign / pause / resume / restart / restart_all / sync` 后交给 `QueueSupervisor`。

`QueueSupervisor` 是本机 Worker 生命周期管理器：

- 每个队列一个独立 Worker 进程。
- 支持注册、暂停、恢复、重启、卸载。
- 暂停采用协作式排空：先停止 RabbitMQ 拉取，再等待已接收任务完成。
- 排空默认超时可配置，当前模板为 1800 秒。
- Worker 异常会反映为 `FAILED` 状态，可通过恢复或重启替换进程。

`app.control.worker.run_queue_worker` 是子进程入口：

1. 创建 `PausableRabbitmqConsumer`。
2. 建立 RabbitMQ 消费订阅。
3. 向父进程上报 `ready`。
4. 持续检查消费错误和本地 `drain` 命令。
5. 排空完成后向父进程上报 `paused` 或错误。

### 6.4 队列消费与消息协议

`app.queue.consumer.handle_message` 是单条消息入口：

1. 过滤单号中包含 `TEST` 的测试任务。
2. 调用 `build_task_context(task)` 解析消息。
3. 使用 `execution_log_session(context)` 开启执行日志会话。
4. 通过 `AccountSessionCoordinator.acquire_slot` 获取账号浏览器槽位。
5. 调用 `dispatch_context(context)` 路由到具体船司任务。
6. 释放浏览器槽位。

消息解析要求的核心字段：

| 字段 | 用途 |
| --- | --- |
| `rpaTaskTopic` | 完整队列名，用于路由 |
| `rpaMessageId` | 消息唯一标识，也是日志记录标识 |
| `websiteInfo` | 网站、账号和登录相关上下文 |
| `content` | 业务填单内容 |
| `id` | 回传任务 ID |
| `rpaOperate` / `customerRole` | 可选业务操作和客户角色 |

全局路由器会扫描 `app.spider.*.router` 中的 `ROUTES`，按完整队列名精确匹配，并检查重复路由。

当前源码中已配置的入口：

| 队列 | 客户 | 船司目录 | 业务 |
| --- | --- | --- | --- |
| `FHT_MSCGW_SI` | `FHT` | `app/spider/MSCGW` | SI 填单/提交 |
| `QTCT_ZIM_SI` | `QTCT` | `app/spider/ZIM` | SI |
| `QTCT_ZIM_VGM` | `QTCT` | `app/spider/ZIM` | VGM |

`message_list/` 中还有 `ASY_EMC_SI`、`FHT_HPL_SI`、`JH_HPL_SI` 等样例，但它们不等于当前源码已注册的路由。

### 6.5 任务基类与执行生命周期

`BaseRpaTask` 是船司任务的通用生命周期基类，主要流程包括：

1. 可选发送“处理中”通知。
2. 由 `BrowserManager` 启动或接管浏览器。
3. 初始化 DOM、HTTP、截图助手。
4. 执行具体任务类实现的 `login()`。
5. 登录完成后释放登录闸门。
6. 执行业务方法。
7. 收集业务附件、截图和录屏文件。
8. 上传文件到 OSS 或降级到局域网文件存储。
9. 构造并发布 `TaskResult`。
10. 上报执行日志终态。

结果相关状态和字段集中在 `app.core.task.result.TaskResult`。错误类型包括登录失败、元素未找到、表单校验失败、业务错误、未填字段、结果回传失败等。

### 6.6 账号会话与浏览器资源

`app/core/scheduler/account_session.py` 中的 `AccountSessionCoordinator` 使用多进程管理器托管，跨队列 Worker 共享状态：

- 按 `websiteInfo.id + 船司` 等信息生成账号会话键。
- 同一账号默认最多 3 个浏览器槽位。
- 第一条任务使用主用户目录；并发槽位使用独立临时目录。
- 首次登录完成前，后续任务等待登录闸门。
- 登录失败时只允许一个等待任务尝试重新登录。
- 账号空闲后可回收临时浏览器目录。
- 支持每日固定时间清理空闲浏览器，并等待忙碌任务结束。

`BrowserManager` 使用 DrissionPage 的 `ChromiumOptions` 和 `Chromium`：

- 使用租约中的调试端口和用户数据目录。
- 为本次队列消息建立独立下载目录。
- 支持代理、无痕模式、页面加载策略。
- 启动后登记浏览器 PID，便于录屏和清理。

### 6.7 录屏与页面工具

`app/core/page/recorder.py` 调用 `capturesdk.CaptureSDKClient`：

- 通过 DrissionPage 页面获取浏览器 PID。
- 查找可见浏览器窗口 HWND。
- 按任务生成 MP4 文件名。
- 录制分辨率默认 1920x1080、10 FPS、CPU 编码。
- 停止后校验输出文件存在且非空。

`app/core/page` 还提供：

- `DomHelper`：页面元素、下载和文件处理辅助。
- `HttpHelper`：浏览器上下文中的 HTTP 辅助。
- `Screenshot`：截图和失败截图上传辅助。
- `wait.py`：等待工具。

### 6.8 执行日志 Agent 端实现

`app/core/logging/log_session.py`：

- 只在队列模式且 `RPA_LOG_SERVICE_ENABLED=true` 时启用。
- 本地调试 `runtime_mode='local'` 强制关闭。
- 从 `TaskContext` 构建日志上下文。
- 在消费入口创建 `RUNNING` 执行记录。
- 异常退出时兜底写入 `FAILED` 终态。
- 使用 ContextVar 绑定当前执行上下文。

`app/core/logging/report_client.py`：

- 进程内单例 `LogReportClient`。
- 后台线程攒批，满 50 条或约 1 秒发送一次。
- `POST /api/v1/logs/batch` 批量上报日志。
- `POST /api/v1/executions/finish` 上报终态。
- 上报失败只打印警告，不向上抛异常，不阻塞 RPA 业务。
- 队列最大容量 20000，满时丢弃并记录累计丢弃数量。
- 进程退出时 `atexit` 调用 `flush()`。

设备名解析顺序：

1. `RPA_LOG_DEVICE_NAME`
2. `QUEUE_CONTROL_DEVICE_ID`
3. 主机名

### 7.3 Redis Streams 协议

命令流：

```text
queue-control:commands:<DEVICE_ID>
```

事件流：

```text
queue-control:events
```

`RedisStreamBus` 使用消费组读取消息：

- 平台向设备专属命令流发送 JSON 命令。
- Agent 读取并确认命令。
- Agent 向统一事件流发布注册、状态、心跳和命令结果。
- `EventProcessor` 读取事件流，落库成功后才 ACK。
- 心跳时平台对比期望分配与设备实际上报，不一致则补发 `sync`。

### 7.4 控制台 API

旧路径风格的设备/队列控制 API：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/dashboard` | 设备、队列和状态总览 |
| `POST` | `/api/devices` | 注册设备 |
| `POST` | `/api/devices/{device_id}/queues` | 分配队列 |
| `DELETE` | `/api/devices/{device_id}/queues/{queue_name}` | 解除队列分配 |
| `POST` | `/api/devices/{device_id}/queues/{queue_name}/commands` | 暂停/恢复/重启 |
| `POST` | `/api/devices/{device_id}/commands/restart-all` | 重启设备全部队列 |
| `GET` | `/healthz` | 数据库健康检查 |

RPA 日志模块统一挂在 `/api/v1` 下。

### 7.5 RPA 日志数据模型

`queue_control_platform/server/rpa_log/init_db.py` 幂等创建 5 张表：

| 表 | 用途 |
| --- | --- |
| `rpa_execution` | 每次消息执行一条主记录 |
| `rpa_execution_log` | 执行过程日志明细 |
| `rpa_execution_file` | 录屏、截图和业务记录文件 |
| `rpa_device` | 日志模块设备维表 |
| `rpa_queue` | 日志模块队列维表 |

重要规则：

- 当前实现已取消 `(rpa_message_id, queue_name)` 唯一键；同一消息重复消费会插入新的执行记录。
- 单条执行记录的 `finish` 仍然幂等，首次终态生效，重复终态返回冲突。
- 状态包括 `RUNNING`、`SUCCESS`、`FAILED`，并保留 `TIMEOUT` 扩展状态。
- 失败原因来自任务结果 `remark`。
- 失败截图 URL、日志数量、开始时间、结束时间和耗时都落在主记录上。
- 文件 URL 支持完整 OSS 地址或局域网 `/files/*` 地址。

### 7.6 RPA 日志 API

Agent 上报接口使用 Bearer Token：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/executions` | 创建执行记录 |
| `POST` | `/api/v1/logs/batch` | 批量追加日志 |
| `POST` | `/api/v1/executions/finish` | 写入终态和记录文件 |

Web 查询接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/executions` | 分页查询执行记录 |
| `GET` | `/api/v1/execution/detail` | 查询主记录、日志和文件 |
| `GET` | `/api/v1/devices` | 设备列表和统计 |
| `GET` | `/api/v1/queues` | 队列列表和统计 |
| `GET` | `/api/v1/stats/summary` | 今日执行统计 |

文件服务：

- `/files/*` 挂载 `RPA_LOG_FILES_DIR` 指向的本地目录。
- 用于局域网文件降级存储和只读访问。

## 9. `capturesdk`：Windows 录屏 SDK

`capturesdk` 是 Windows 录屏能力封装：

- `CaptureSDKClient` 调用 `CaptureSDK.Cli.exe`。
- 支持列举浏览器窗口、按 PID 查找 HWND、按调试端口定位浏览器进程。
- `CaptureSession` 封装录屏生命周期，支持启动、状态查询、停止和上下文管理。
- 第三方 FFmpeg DLL 位于 `capturesdk/third_party/ffmpeg/bin`。
- `README.md` 说明当前 FFmpeg 桥接阶段仍有部分能力被刻意延后。
- 该模块包含 Windows 可执行文件和 DLL，不适合作为 macOS 本地运行路径的一部分。

## 10. 本地运行与部署

### 10.1 安装依赖

```bash
uv sync
```

### 10.2 启动本地 MySQL 和 Redis

```bash
docker compose -f queue_control_platform/docker/compose.yml up -d
```

Compose 提供的服务：

```bash
uv run python -m queue_control_platform.server.main
```

平台会初始化所需表结构，启动 Redis 事件处理器，并在 `8766` 提供控制台和日志服务。

```bash
cd rpa-log-web

```

构建完成后重启中心平台，即可由后端托管前端页面。

### 10.5 启动设备侧 Agent

```bash
uv run python -m app.main
```

## 12. 当前实现状态与风险

### 12.1 已具备的能力

- 分布式设备注册与队列分配。
- 每队列独立 Worker 进程。
- 协作式暂停、恢复和重启。
- RabbitMQ 任务消费与动态路由。
- 账号级浏览器槽位与登录并发控制。
- 浏览器端口、profile、下载目录和日清理管理。
- 截图、录屏、文件上传和结果回传。
- 执行日志集中持久化与 Web 查询。
- React 管理前端与中心平台合并部署。
- 本地兜底队列模式。
- Docker Compose 本地基础设施。

### 12.2 需要关注的问题

1. **过期测试影响 CI 可用性**
   - 5 个测试文件引用已删除的 flow/deploy 模块。
   - 建议删除、重命名或补齐对应实现，否则默认 `pytest` 无法形成稳定质量门禁。

2. **日志上报客户端存在测试失败**
   - 40 个用例通过，但日志攒批用例失败。
   - 需要确认是测试竞争还是 `flush()` 与后台线程的并发边界问题。

3. **文档存在历史差异**
   - `doc/CodeWiki.md` 和部分历史设计仍描述 WHL 等模块或旧目录。
   - 当前源码路由只看到 MSCGW 与 ZIM。
   - 阅读时应以 `app/spider/*/router.py` 为准。

4. **平台测试依赖本地 MySQL**
   - 本地未启动 MySQL 时 17 个平台测试全部跳过。
   - CI 或发布前应确保 MySQL 测试环境可用。

5. **Windows 资产混入跨平台仓库**
   - `capturesdk` 包含 `.exe` 和 `.dll`。
   - 逻辑封装可以跨仓库维护，但二进制运行时需要明确分发、许可和平台边界。

6. **敏感配置风险**
   - `.env.example` 中包含示例设备 Token，真实环境必须轮换。
   - `.env` 不应提交；设备注册令牌、数据库口令、RabbitMQ 口令需要通过安全方式管理。
