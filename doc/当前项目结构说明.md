# Wise RPA 当前项目结构说明

> 文档基于当前代码树整理，最后核对日期：2026-09-18。
> 本文描述现行实现，不以历史设计文档或旧版 README 中的目录为准。

## 1. 项目定位

Wise RPA 是一个面向船司单证业务的 Python 浏览器自动化系统。项目当前由三个运行部分组成：

1. **业务 RPA 应用**：从 RabbitMQ 接收任务，解析消息并按队列路由到对应船司业务。
2. **设备侧队列控制 Agent**：在实际执行任务的机器上运行，负责接收中心命令，并为每个已分配队列管理独立 Worker 进程。
3. **中心队列控制平台**：提供维护页面、设备注册、队列分配、暂停/恢复/重启 API，并将设备状态写入 MySQL。

业务执行依赖 RabbitMQ、Redis、Nacos、浏览器和可选的 OSS/验证码/通知服务；中心控制平台额外依赖 MySQL 和 Redis。

## 3. `app` 业务应用

### 3.1 应用入口

```text
app/
├── main.py                     # 设备侧 Queue Agent 的入口
├── config/                     # 环境变量、Nacos 和 RabbitMQ 配置
├── control/                    # Agent、Supervisor 和 Worker 生命周期
├── queue/                      # RabbitMQ/Funboost 消费和结果消息
├── core/                       # 与船司无关的任务、浏览器、页面和集成能力
├── spider/                     # 按船司组织的登录和业务任务
├── dev/                        # 本地消息调试入口
└── utils/                      # 小型通用工具
```

`app.main` 当前并不直接从环境变量启动固定队列集合，而是转到 `app.control.queue_client.main` 启动设备侧控制客户端。默认 `QUEUE_ASSIGNMENT_SOURCE=server` 时，中心平台通过 Redis Streams 下发队列分配，Agent 再创建对应的 Worker；`local` 模式则直接按 `RPA_QUEUES` 监听。

### 3.2 配置层：`app/config`

| 文件 | 职责 |
| --- | --- |
| `__init__.py` | 加载项目 `.env`；默认按 `NACOS_ENABLED` 决定是否加载 Nacos 环境配置。 |
| `nacos_config.py` | 从 Nacos 读取共享数据源、RabbitMQ 和爬虫相关配置，并写入环境变量。 |
| `rabbitmq.py` | 定义 `RabbitmqSettings`，统一生成 RabbitMQ 连接参数和 URL。 |
| `settings.py` | 读取浏览器端口、下载目录、队列并发、QPS、账号并发和浏览器日清理等本地运行参数。 |
| `queue_config.py` | 解析 `QUEUE_ASSIGNMENT_SOURCE` 与 `RPA_QUEUES`，兼容旧的固定队列启动方式。 |
| `types.py` | 环境变量布尔值转换。 |

配置加载的大致顺序是：加载 `.env` -> 按开关加载 Nacos -> 各运行组件读取自身配置。RabbitMQ 的默认来源是 Nacos；中心平台的 MySQL、Redis、监听地址主要从 `.env` 读取。

### 3.3 设备控制层：`app/control`

```text
app/control/
├── queue_client/
│   ├── main.py                  # Agent 命令行入口
│   ├── client.py                # 注册、心跳、命令消费和事件上报
│   ├── config.py                # 设备 ID、注册令牌、Redis 和项目路径
│   └── redis_client.py          # Redis Streams 命令/事件读写
├── supervisor.py                # 一个队列一个 Worker 进程的监管器
└── worker.py                    # 子进程入口，启动单队列消费者并处理排空
```

核心职责如下：

- `QueueControlClient` 向中心发送心跳，接收 `sync`、`start`、`pause`、`resume`、`restart` 等命令。
- `QueueSupervisor` 为每个队列维护独立的操作系统进程、运行状态、命令队列和事件队列。
- `worker.py` 在子进程中创建 RabbitMQ 消费者；暂停或重启时先停止拉取新消息，再等待已接收任务排空。
- 所有队列 Worker 共享设备级的账号会话协调器，用于限制同一 `websiteInfo.id + 船司` 的浏览器并发和凭据登录竞争。
- 协调器在设备 Agent 进程内启动浏览器日清理后台线程，Worker 只使用共享槽位，不各自调度清理。

### 3.4 队列层：`app/queue`

| 文件 | 职责 |
| --- | --- |
| `consumer.py` | 构建单队列消费者，解析任务消息，获取账号浏览器槽位并调用统一分发器。 |
| `booster.py` | 定义项目使用的 Funboost 参数，包括 RabbitMQ、并发数、QPS 和死信参数。 |
| `pausable_rabbitmq.py` | 对 Funboost RabbitMQ 消费循环增加可协作排空能力。 |
| `rabbitmq.py` | 注册携带死信交换机参数的自定义 RabbitMQ Publisher。 |
| `publisher.py` | 对外暴露任务结果发布器。 |
| `message.py` | 校验任务消息并构建 `TaskContext`。 |

单条消息的主要路径是：`consumer.handle_message` -> `build_task_context` -> 获取账号会话槽位 -> `dispatch_context` -> 船司路由 -> 任务类 `run()`。

`BaseRpaTask.run()` 是业务任务的模板方法，负责初始化浏览器和页面辅助器、登录、录屏、执行业务、失败截图、文件上传以及最终结果发布。船司任务主要实现 `login()` 和 `execute_business()`，并通过选择器和字段校验辅助完成页面操作。

浏览器资源由设备级 `AccountSessionCoordinator` 统一管理：

- 同一 `websiteInfo.id + 船司` 最多占用 `ACCOUNT_MAX_CONCURRENT` 个浏览器槽位。
- 主 profile 长期复用；临时 profile 位于 `runtime/browser_profiles/.ephemeral/`，空闲超过 `ACCOUNT_IDLE_SECONDS` 后回收。
- `BrowserCleanupScheduler` 按本地时区每天在 `BROWSER_CLEANUP_TIME`（默认 `20:30`）触发一次清理。
- 清理期间会挡住新的槽位申请，并等待忙碌任务最多 `BROWSER_CLEANUP_WAIT_BUSY_SECONDS`（默认 1800 秒）。
- 清理对象是空闲槽位和孤儿 RPA Chromium 进程；主 profile 目录保留，下次任务重新拉起浏览器。忙碌槽位超时后跳过，避免误杀正在执行的任务。
- 进程匹配依据 `--user-data-dir` 是否落在本机 RPA profile 根目录，或调试端口属于已分配端口；不会按进程名误杀用户自己的 Chrome。
- 需要立刻清理时可执行：`uv run python -m app.core.scheduler.browser_cleanup`。

中心平台的数据和通信边界：

- MySQL 保存设备、队列绑定、期望状态、控制命令和最新状态快照。
- Redis Stream `queue-control:commands:<DEVICE_ID>` 保存发往指定设备的命令。
- Redis Stream `queue-control:events` 保存 Agent 的心跳、队列状态和命令结果。
- `EventProcessor` 只有在事件处理完成后才确认 Redis 消息；设备重新心跳后，中心发送完整分配快照帮助 Agent 恢复。

## 8. 运行关系

### 8.1 生产/队列模式

```text
中心维护页面
    │ FastAPI + MySQL
    │ Redis Streams
    ▼
设备 Queue Agent（app.main）
    │ QueueSupervisor：一个队列一个进程
    │ AccountSessionCoordinator：共享浏览器槽位 + 日清理线程
    ▼
单队列 Worker（app.control.worker）
    │ PausableRabbitmqConsumer + Funboost
    ▼
RabbitMQ
    │ task JSON
    ▼
TaskContext → 动态船司路由 → BaseRpaTask → 浏览器/页面操作
    │
    ├── 处理中通知
    ├── 截图、录屏和 OSS 文件
    └── 任务结果回传
```

### 8.2 单条任务生命周期

1. Worker 从 RabbitMQ 接收 JSON，并由 `build_task_context()` 校验队列名、消息 ID、站点信息和业务内容。
2. `AccountSessionCoordinator` 为 `websiteInfo.id + carrier` 分配浏览器槽位和 profile；若正在日清理，则等待清理闸门放开。
3. `resolve_queue_route()` 扫描船司路由表，确定客户、船司、业务和具体 handler。
4. `BaseRpaTask.run()` 启动/接管浏览器，执行登录和业务操作。
5. 失败时尽力截图；任务结束时停止录屏、上传过程文件，并由 `ResultPublisher` 发布结果。
6. Consumer 释放账号会话租约，RabbitMQ 消息进入正常 ACK/NACK 生命周期。

### 8.3 浏览器日清理

```text
每天 BROWSER_CLEANUP_TIME（默认 20:30）
    │ BrowserCleanupScheduler
    ▼
AccountSessionCoordinator.cleanup_stale_browsers()
    │ 设置 cleanup_hold，挡住新槽位
    │ 等待忙碌任务，最多 BROWSER_CLEANUP_WAIT_BUSY_SECONDS
    ▼
终止空闲槽位 PID + 匹配到的孤儿 RPA Chromium
    │ 删除空闲临时 profile
    │ 保留主 profile 目录
    ▼
放开 cleanup_hold，后续任务重新启动浏览器
```

## 9. 关键配置和启动入口

### 9.1 启动入口

```bash
# 本地业务消息调试
uv run python -m app.dev.local_runner --message ./message_list/msg_demo.json

# 启动设备侧 Queue Agent
uv run python -m app.main

# 启动中心控制平台
uv run python -m queue_control_platform.server.main

# 启动本地 MySQL 和 Redis
docker compose -f queue_control_platform/docker/compose.yml up -d

# 立即清理本机 RPA 浏览器（不等待忙碌任务）
uv run python -m app.core.scheduler.browser_cleanup
```

### 9.2 重要环境变量

| 配置 | 作用 |
| --- | --- |
| `NACOS_ENABLED` | 是否加载 Nacos 环境配置。 |
| `RABBITMQ_CONFIG_SOURCE` | RabbitMQ 配置来源标识；当前默认流程仍由 Nacos 提供连接信息。 |
| `QUEUE_ASSIGNMENT_SOURCE` | 队列监听来源：`server` 走中心下发，`local` 走本地 `RPA_QUEUES`。 |
| `RPA_QUEUES` | 本地队列集合；`local` 模式的唯一来源，`server` 模式下作为控制面失联兜底。 |
| `QUEUE_CONTROL_DEVICE_ID` / `QUEUE_CONTROL_DEVICE_TOKEN` | 设备 Agent 注册身份（`server` 模式必填）。 |
| `QUEUE_CONTROL_REDIS_URL` | Agent 与中心平台共用的 Redis 地址。 |
| `QUEUE_CONTROL_MYSQL_URL` | 中心平台 MySQL 连接地址。 |
| `QUEUE_CONCURRENT_NUM` / `QUEUE_QPS` | 单队列 Funboost 并发数和启动速率。 |
| `ACCOUNT_MAX_CONCURRENT` | 同一设备内账号会话的最大浏览器槽位数。 |
| `ACCOUNT_IDLE_SECONDS` | 临时浏览器槽位的空闲回收时间，默认 60 秒。 |
| `BROWSER_USER_DATA_DIR` | 主 profile、端口注册表和临时 profile 根目录。 |
| `BROWSER_PORT_START` / `BROWSER_PORT_END` | 浏览器调试端口池。 |
| `BROWSER_CLEANUP_ENABLED` / `BROWSER_CLEANUP_TIME` | 是否启用浏览器日清理及每天执行时刻，默认 20:30。 |
| `BROWSER_CLEANUP_WAIT_BUSY_SECONDS` | 日清理等待忙碌任务结束的最长时间，默认 1800 秒。 |
| `ENABLE_BROWSER` | 本地配置项；本地骨架调试时通常关闭真实浏览器。 |

## 10. 当前维护注意事项

1. 默认 `QUEUE_ASSIGNMENT_SOURCE=server` 时，正式队列发现方式仍是“中心平台分配给设备”；`RPA_QUEUES` 作为控制面失联兜底，或在 `local` 模式下作为唯一监听来源。
2. 当前真实船司目录是 `app/spider/ZIM` 和 `app/spider/MSCGW`。历史文档中出现的 `app/Spider/WHL`、`FL_WHL` 等路径属于旧架构或历史设计，不能作为当前代码入口。
3. 现行自动化测试入口是 `tests/test_browser_cleanup.py` 和 `tests/test_queue_assignment_source.py`。修改队列控制、账号会话、浏览器清理或任务生命周期后应先跑这些测试，并至少通过本地消息调试验证路由。
4. `runtime/` 下可能含账号 profile、任务消息、截图和日志，提交代码或分享日志前应检查敏感信息。
5. RabbitMQ 队列声明包含死信交换机参数，修改 `app/queue/booster.py` 或 `app/queue/rabbitmq.py` 前需要确认线上已有队列属性，否则可能触发队列参数不一致错误。
6. 浏览器日清理只终止属于本机 RPA profile 根目录或已分配调试端口的 Chromium；不要用无差别 `killall chrome` 代替。主 profile 目录会保留，因此清理后的下一次任务会重新启动浏览器而不是复用旧进程。

## 11. 推荐阅读顺序

1. `app/main.py`、`app/control/queue_client/client.py`：理解设备 Agent 启动和控制命令。
2. `app/control/supervisor.py`、`app/control/worker.py`：理解队列进程生命周期。
3. `app/queue/consumer.py`、`app/queue/message.py`：理解 RabbitMQ 消息进入业务的方式。
4. `app/core/task/router.py`、`app/core/task/dispatcher.py`：理解动态船司路由。
5. `app/core/task/base_task.py`：理解浏览器任务的统一生命周期。
6. `app/core/scheduler/account_session.py`、`app/core/scheduler/browser_cleanup.py`、`app/core/browser/manager.py`、`app/core/browser/process.py`：理解账号并发、浏览器资源和日清理。
7. `app/spider/ZIM/`、`app/spider/MSCGW/`：阅读具体业务实现。
8. `queue_control_platform/server/`：需要维护中心控制平台时再阅读其 API、事件和持久化实现。
